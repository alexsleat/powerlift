**Batch 6 done (2026-08-17):** history-page safety + a real write path (v1.5.0). Superseded the whole-schema PUT for everyday saves.
- `PUT /data/schema` did `DELETE FROM e1rm_log` + `deleteAbsent` on sessions/instances/maxes on EVERY save — authoritative full replace, so a stale client could delete server rows, and payload grew with history toward the 2 MB nginx/express cap (~300-400 sessions) and `MAX_ROWS 5000` (~600). Now restore/import only.
- New incremental endpoints in data.js: `PUT/DELETE /sessions/:id` (session + its e1rm rows + optional instance, one transaction), `PUT/DELETE /instances/:id`, `PATCH /profile`, `PUT/DELETE /lift-maxes/:exerciseId`, `PUT /custom-exercises`. Per-entity caps (`MAX_SESSIONS_PER_USER` 20000, `MAX_INSTANCES_PER_USER` 500, `MAX_ENTITY_BYTES` 200000) replace the per-request MAX_ROWS guard.
- `src/sync.js` = offline cache + outbox of small idempotent ops, keyed for coalescing, FIFO with backoff, retry on online/refocus, dead-letter for permanent 4xx (surfaced in Settings → Sync). `src/schemaOps.js` diffs old vs new schema into ops, so App's single `updateSchema` path stays — relies on React spread preserving object identity for unchanged entities, and on NOTHING mutating schema state in place (verified none does; a mutation would produce an empty diff and silently lose the change).
- Deploy skew is handled both ways: old client + new server uses the still-present PUT /schema; new client + old server gets 404 on an incremental op and falls back to one whole-schema PUT.
- Also: `user_profile.prefs` TEXT column added (idempotent migration in db.js) — theme/rep_ranges/history-strip settings were written by the client and silently dropped, since only 4 typed columns were persisted and returned.
- Tests: `src/schemaOps.test.js` + `npm test` (`node --test`, no deps). 11 tests covering the diff and outbox coalescing.
